# STDLIB.md

Every place `logq` would normally reach for a third-party package, and what
it uses from the Go standard library instead. This ledger is built
incrementally — each row is added in the same commit that introduces the
substitution, not backfilled at the end, so the `git log` itself is the
evidence trail for the rationale below.

| Would-be dependency | logq uses instead | Rationale |
|---|---|---|
| `stretchr/testify` | `testing` + table-driven tests + `t.Run` subtests | Go ships a full test framework; a third-party assertion library buys nothing but an import, and zero test dependencies means nothing to disclose under the rules' dev-dependency carve-out either. |
| a hand-rolled duration-unit grammar | stdlib `time.ParseDuration` | The lexer tokenizes a duration literal permissively (digit run + letter-run suffix, e.g. `1h30m`, `-1h`) and keeps it as raw text in the AST; no custom unit-parsing logic exists anywhere. Validating/converting that text happens via `time.ParseDuration` once the evaluator lands (Phase 3+) — a subtraction from the original design, not an addition, and it gets compound-unit support (`1h30m`) for free instead of needing to hand-write it. |
| `agnivade/levenshtein` | Own ~25-line DP edit-distance function (`EditDistance`), collapsed to two rows | Powers "did you mean 'exists'?"-style diagnostics; a whole package for one well-known, easily-hand-written algorithm isn't worth the import. Radius capped at 2 and ties suppressed (per spec) so a wrong guess is never worse than no guess. |
| a hand-rolled regex matcher | stdlib `regexp` (RE2 class), compiled once per query at `Compile` time | `~`/`!~` need real regex matching, and stdlib already provides exactly the right safety property for untrusted log-derived patterns: RE2's automaton-based matching guarantees linear time in input size — no catastrophic backtracking, unlike a naive backtracking engine. Composing it correctly (compile once, reuse per record) is the craft here, not reinventing the matcher. |
| **`tidwall/gjson` — 10,420 known importers on pkg.go.dev, live-verified 2026-08-29** | `encoding/json` (`json.Decoder.Token()`) → a hand-written ordered map + `json.Number` int64/float64 discipline | gjson exists because `encoding/json`'s default `map[string]any` unmarshal is unordered and always decodes numbers to float64 — silently corrupting a large integer field (a snowflake ID, for instance) and discarding the source document's key order. Streaming through `Decoder.Token()` into our own ordered `Record`, with `json.Number` chosen deliberately over the float64 default, gets both properties back from stdlib alone: order preserved, big integers exact. This is the project's single clearest Package Killer case — gjson's core value proposition, replaced with ~150 lines built directly on the decoder gjson itself wraps. |
| the well-known `bufio.Scanner` 64KB `MaxScanTokenSize` trap | `bufio.Reader.ReadSlice`, hand-rolled line splitting | The naive fix (`scanner.Buffer(buf, largerMax)`) only raises the ceiling — a `Scanner` still just stops dead (`Scan()` returns `false`, `Err()` holds `ErrTooLong`) on anything past that new ceiling, silently ending the whole run unless the caller remembers to check `Err()`. Built on `bufio.Reader` directly instead, so one oversized line is skipped, counted, and reading resumes cleanly at the next line — never a silent early stop, never a full-line memory spike either (the oversized remainder is discarded via `ReadSlice`'s buffer-full signal, not first fully read then thrown away). |
| `spf13/cobra` + `pflag` | stdlib `flag` (`flag.NewFlagSet`), short/long aliases bound to the same variable | Two flags deep (`-f`/`--format`, `-o`/`--output`) plus help/version — cobra's full command tree and 30-transitive-dep footprint buys nothing here that `flag.NewFlagSet` with `ContinueOnError` doesn't already give directly: custom usage text, controlled exit codes, no framework-owned `os.Exit` calls to fight. |
| `go-logfmt/logfmt` | Own ~150-line hand-written state machine (`internal/logfmtx`) over the spec's named Key/PreVal/Val/QVal/QEsc/AfterVal states | logfmt has no formal grammar spec of its own to lean on (unlike JSON/CSV) — the "correct" behavior is exactly what a small, well-tested state machine defines. Every error (bare token, empty key, invalid key character, unterminated quote, unknown escape, missing whitespace after a quoted value) is positioned to a byte offset, not just "malformed line." |
| a third-party fuzzing framework (pre-Go-1.18 tooling like `go-fuzz`) | stdlib native fuzzing (`testing.F`, `go test -fuzz=`) | Coverage-guided fuzzing has been in the standard library since Go 1.18 — no external harness, corpus format, or build step needed. `FuzzLogfmtRoundTrip` proves the logfmt decoder's escape handling holds for arbitrary byte sequences (including invalid UTF-8 and raw NUL bytes), not just the 13 hand-picked seeds. |
| `klauspost/compress` | stdlib `compress/gzip` | Honesty note, not just a substitution: klauspost's gzip implementation is measurably faster (~2×) than stdlib's. Disclosed here on purpose rather than silently picked — decode throughput at real log-file scale is dominated by JSON/logfmt decoding and line splitting, not gzip inflate, so the difference is real but not the bottleneck it would be in a pure-decompression tool. `compress/gzip.Reader` also gets multi-member stream support for free (`Multistream` defaults to `true`), which is the actual behavior this project needs. |
| `araddon/dateparse` | A fixed, explicit `time.Parse`/`time.ParseInLocation` layout table (`internal/eval/timestamp.go`), plus a hand-written numeric epoch heuristic | dateparse's whole pitch is "guess the format automatically" — which is exactly the kind of magic this project avoids by design: an auditable, ordered ladder of named layouts (RFC3339Nano → … → nginx CLF → epoch heuristic) is deterministic and testable row-by-row, where a guessing library's behavior on an ambiguous string is an implementation detail you don't control. |
| a bundled/vendored copy of the IANA tzdata (some ecosystems ship one to avoid depending on the host) | stdlib `time/tzdata`, blank-imported in `cmd/logq/main.go` | `--tz` needs the full IANA zone database to resolve names like `America/New_York`, and can't assume the *host* has one — a minimal container, a scratch image, or (as tested directly) this very Windows dev machine may have none. `time/tzdata` embeds the whole database into the compiled binary itself (~800KB–1MB, disclosed) via one blank import — no vendored copy, no runtime download, no dependency on `/usr/share/zoneinfo` existing at all. This is what actually makes "one static binary, runs anywhere" true rather than aspirational. |
| container libraries offering a generic priority-queue/bounded-top-K type | stdlib `container/heap`, wired directly onto `Sort` (`internal/pipeline/sort.go`) | `sort ... limit N` must materialize at most N records (§7), not the whole filtered stream — that's a bounded top-K, exactly what `container/heap` is for. Composing the standard 5-method `heap.Interface` onto the stage's own record slice needs zero extra allocation for a wrapper type. Top-K over aggregate groups (§8.5: `stats ... | sort <aggcol> desc | limit K`) reuses this exact same stage unchanged — each group is just another `Record` flowing through the pipeline, so no second, parallel heap implementation exists anywhere in the codebase for that case. |
| `olekukonko/tablewriter` | stdlib `text/tabwriter` | Tabwriter *is* the terminal table — column-width alignment via tab-stop expansion is exactly what it was built for. The one real gap: it only supports table-wide alignment (`AlignRight`), not mixed per-column alignment, and this project wants numeric columns right-aligned alongside left-aligned text columns. Closed by hand-padding just the numeric cells to their column's max width before handing everything to tabwriter, rather than reaching for a fuller third-party table library over one missing feature. |
| a random-seeded hash (`hash/maphash`, the stdlib SipHash-class answer to hash-flooding) *and* stdlib `hash/fnv` | a ~10-line hand-rolled, salted FNV-1a (`internal/agg/distinct.go`) | `count_distinct` needs a hash keyed against attacker-controlled log field values (the same hash-flooding attack class that forced Node.js/PHP/Python/Java toward randomized hash seeds after the 2011-12 disclosure wave) — ruling out a bare, public-constant FNV-64a. But a genuinely RANDOM per-process seed (what `hash/maphash` gives you) would let two runs over identical input diverge on the astronomically rare collision-boundary case at full 65536-item cap saturation (≈1.16×10⁻¹⁰), breaking this project's own batch-mode determinism guarantee (§15). The fix is a FIXED, documented salt XORed into the offset basis instead — but `hash/fnv`'s public API doesn't expose a way to set a custom offset basis, so achieving that literally means implementing FNV-1a's five-line algorithm by hand rather than working around stdlib's API to fake the same effect. "Keyed, not secret" — stated plainly, not oversold as a cryptographic guarantee it isn't. |
| an approximate-percentile/sketch library (e.g. t-digest, DDSketch) | a from-scratch Vitter's **Algorithm L** reservoir sampler (`internal/agg/percentile.go`), seeded via stdlib `math/rand` | p50/p95/p99 need to stay bounded in memory (O(cap)) over a stream that can be bigger than RAM, without materializing every value. Algorithm L (J.S. Vitter, "Random Sampling with a Reservoir," ACM TOMS 11(1), 1985) is deliberately named and cited precisely — it is explicitly NOT "Algorithm R," the older Waterman/Knuth reservoir algorithm that draws one random number per incoming item (a mis-citation caught and corrected during this project's own v1.1 research pass). L instead computes a skip-gap directly, needing only O(k·(1+log(N/k))) random draws for the whole stream — a real asymptotic win at billions of records. The reservoir is fixed-seeded (not wall-clock/process-entropy seeded) so batch-mode output stays byte-identical across runs (§15), and nearest-rank selection on the sorted sample (never linear interpolation) means the reported percentile is always an actual observed value, never a synthesized average. |
| a graceful-shutdown/process-supervisor package (e.g. `oklog/run`, `golang.org/x/sync/errgroup` for the signal-handling piece specifically) | stdlib `signal.NotifyContext` + a small raw `signal.Notify` watch for the second-signal case (`cmd/logq/main.go`) | §14's two-tier interrupt policy (first signal: stop intake, flush partial results, exit 130; a genuinely impatient second signal within 2s: exit immediately, no flush) needs exactly one thing `signal.NotifyContext` doesn't give alone — reacting to a SECOND occurrence of the same signal after the context it manages is already cancelled (`NotifyContext` only ever fires its cancellation once, on the first). A raw `signal.Notify` channel armed only after `ctx.Done()` fires closes that one gap in ~10 lines, without reaching for a whole supervisor library over one two-tier interrupt policy. |
| a manual `errno`-matching helper library for "is this a broken pipe" | stdlib `syscall`/`errors.Is`/`errors.As`, split per-platform (`cmd/logq/sigpipe_unix.go` / `sigpipe_windows.go`) | Go doesn't deliver `SIGPIPE` as a catchable signal for stdout/stderr writes — it surfaces as an ordinary write error instead, and detecting "the downstream reader closed early" (`logq ... \| head -1`, EC-40) means recognizing that specific error. Unix: `errors.Is(err, syscall.EPIPE)`. Windows has no `SIGPIPE` concept at all, and empirically (measured directly on this dev machine, piped through Git Bash/MSYS `head`) a write past a closed pipe's read end fails with `ERROR_NO_DATA` (`syscall.Errno(232)`), not `ERROR_BROKEN_PIPE` (109) as the name might suggest — that one's more typically a read-side error; both are checked defensively. Genuinely platform-specific, so it's the one place in this codebase using Go build tags (`//go:build windows` / `!windows`) rather than a single portable check. |
| an ecosystem sharding/worker-pool package (e.g. `panjf2000/ants`, a generic goroutine-pool library) | hand-rolled channel-per-shard fan-out (`internal/pipeline/parallel_stats.go`), keyed on `hash/fnv` over the record's own group key | `-j N` parallelizes stats' per-group aggregation math across N independent, lock-free shards — each a full `*Stats` instance, touched only by its own owning goroutine, communicating with the dispatcher exclusively through a buffered channel. A generic worker-pool library solves a more general problem (arbitrary task queues) than this needs: routing is keyed specifically so a given group's records always land on the same shard (never round-robin), which is what keeps the Flush-time merge trivial — no library abstraction would remove that domain-specific routing logic anyway, so there was nothing left for one to actually do. |
| `fsnotify` | a plain `os.Stat` poll loop + `os.SameFile` for rotation detection (`internal/watch/tailer.go`) | `fsnotify` needs cgo on some platforms — a real problem for this project specifically, since this dev machine has no C compiler at all and couldn't even build a cgo dependency (confirmed directly: `go test -race`, which also needs cgo, fails here with `cgo: C compiler "gcc" not found`). A 1-second poll loop is simple, fully portable, and correct: `os.SameFile` is *itself* already a portable stdlib primitive for "is this the same underlying file" (dev+inode on Unix, the file index via `BY_HANDLE_FILE_INFORMATION` on Windows) — no platform-specific code needed for the rotation-detection logic itself, only for opening the file (see the next entry). |
| — (a real bug found and fixed while building the above, not a substitution) | `internal/watch/open_windows.go`: a `syscall.CreateFile`-based open requesting `FILE_SHARE_DELETE` explicitly, vs. `internal/watch/open_unix.go`'s plain `os.Open` | Empirically discovered on this dev machine while writing `Tailer`'s own tests: Go's plain `os.Open` on Windows does **not** set `FILE_SHARE_DELETE`, so `os.Remove`/`os.Rename` against a file `logq -w` holds open both fail with "The process cannot access the file because it is being used by another process." Left unfixed, that's a real, silent Windows-only limitation — an external log rotator could never rotate a file logq was watching, for as long as logq kept it open, directly undermining the EC-42/EC-43 rotation scenarios this whole package exists to handle. Fixed with `syscall.CreateFile` (stdlib `syscall`, no dependency) requesting `FILE_SHARE_READ\|FILE_SHARE_WRITE\|FILE_SHARE_DELETE` explicitly, wrapped back into a normal `*os.File` via `os.NewFile` — matching Unix's own "unlink/rename while open is always fine" behavior, which is the actual invariant `Tailer`'s rotation detection is designed around. Verified broken beforehand and fixed afterward via a direct repro on this machine. |
